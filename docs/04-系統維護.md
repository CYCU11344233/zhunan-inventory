## 1. NO1 揀貨單（`src/picks.js`、`src/routes/picks.js`）

### 1.1 問題

原本出庫是「看揀貨單 → 去搬 → 按確認」，揀貨單只存在畫面上。員工搬完忘了按確認，系統就不知道貨已經不在了；頁面一關，連「有一張單子沒回報」都查不到。這和大黑板時代「忘了把牌子掛回去」是同一個問題。

### 1.2 做法：發單 → 回報，兩步都寫進資料庫

```
發單（POST /api/picks）                    回報（POST /api/picks/:id/confirm）
  FIFO 算好去哪幾格拿                        這時才寫「出庫」異動、扣庫存
  存成 open 的揀貨單                          單子變成 done
  那幾格的貨被「保留」                        ────────────────
      │                                    取消（POST /api/picks/:id/cancel）
      └─ 沒回報 → 一直是 open，                保留的貨放回來，庫存沒動過
         任何裝置打開都看得到（state.openPicks）
```

- **保留**：還沒回報的單拿走的貨，別張單不會再分配到；那一格也不能移位、不能丟（會提示是哪張單）。這樣員工照單去拿時，貨一定還在。
- **盤點可以改保留中的格子**（盤點反映的是實況）。如果盤點後比單子要拿的少，盤點會回 `warnings` 提醒，那張單回報時也會被擋，要取消重發。
- **復原「出庫」**：貨回到格子，單子回到 open（貨沒出去 = 單子還沒完成）；重做就再變回 done。
- **舊網址** `POST /api/outbound/confirm` 還能用（給舊畫面與測試），等於「發單後馬上回報」，一樣會留下一張已完成的揀貨單。畫面已經改用發單 → 回報，不再呼叫它。

### 1.3 資料表

| 表 | 欄位 | 說明 |
|---|---|---|
| `pick_order` | `id`、`label`、`status`（open / done / cancelled）、`created_at`、`finished_at`、`action_id` | 一張揀貨單。`action_id` = 回報時產生的出庫 action |
| `pick_line` | `pick_id`、`seq`（走路順序）、`batch_id`、`slot_id`、`qty` | 每一站去哪一格、拿哪一批、幾籠 |

「某格被保留幾籠」＝ 所有 open 的單在這格的 `pick_line.qty` 加總。

### 1.4 API

| 方法 | 路徑 | 送什麼 | 回什麼 |
|---|---|---|---|
| POST | `/api/picks` | `{ items: [{ productId, qty }] }` | `{ pick, shortages }` |
| GET | `/api/picks?status=open` | status 可省略（= 全部） | `[pick]`，最新的在前 |
| GET | `/api/picks/:id` | — | `pick` |
| POST | `/api/picks/:id/confirm` | — | `pick`（status = done） |
| POST | `/api/picks/:id/cancel` | — | `pick`（status = cancelled） |

`pick = { id, label, status, createdAt, finishedAt, lines: [{ seq, slotId, batchId, productId, productName, inDate, qty }] }`

`GET /api/state` 多了 `openPicks`（還沒回報的單，舊的在前）。`POST /api/outbound/plan` 的預覽也會扣掉已保留的貨。

## 1.5 NO1 的另一半：放貨單（`src/puts.js`、`src/routes/puts.js`）

進貨也有同樣的問題：系統一按確認就記「已入庫」，但員工可能放到別格、或根本還沒放。所以入庫也改成兩步：

- **發單** `POST /api/puts { items: [{ productId, qty, slotId, expireDate? }] }`：檢查和以前的入庫一樣，另外預定的空格會被保留（別張放貨單、移位、舊的一步入庫都不能佔用）。庫存還沒動。
- **回報** `POST /api/puts/:id/confirm { placements?: [{ seq, slotId }] }`：放好了才建批次（入庫日 = 回報那天）、寫「入庫」異動。現場放到別格就把實際的格子告訴系統，紀錄寫「原定 X，實際放 Y」—— 系統記的永遠是實際位置。
- **取消** `POST /api/puts/:id/cancel`：貨沒進來（退貨、送錯），預定的格子放回來。
- `GET /api/puts?status=open`、`GET /api/puts/:id`；`GET /api/state` 多了 `openPuts`。
- 復原「入庫」→ 放貨單回到 open；重做 → done。
- 舊的 `POST /api/inbound` 還在（= 發單後馬上回報），會留下一張已完成的放貨單。

資料表：`put_order`（和 `pick_order` 同欄位）、`put_line`（`seq`、`product_id`、`qty`、`slot_id` 預定格、`expire_date`、`custom_expire`、`placed_slot_id` 實際格、`batch_id`）。

## 2. NO2 盤點（`src/routes/stocktake.js`）

### 2.1 做法：一次盤一整座倉庫

- 盤點的單位是**一座倉庫**。這座庫每一格有貨的都算盤過了；只要填「和系統不一樣」或「有壞掉」的格子，沒填的 = 點過了、數量正確。
- **全部正確也會留下一筆盤點紀錄**，證明今天盤過了（`GET /api/state` 的 `lastStocktakes` 可以顯示「A 庫今天還沒盤點」）。
- 每一格可以填：
  - `counted`：實際點到幾籠（含壞掉的）→ 和系統不同就寫「盤點」異動（系統 8 → 實際 7）
  - `spoiled`：其中壞掉、不能賣的幾籠 → 寫「丟棄」異動，**一定要寫 `reason`**（例如「腐爛」）
- 有改到庫存時，這些異動是同一個 action，按錯了可以「復原」；盤點紀錄保留，標示已復原。

另外，地圖上的「丟棄」也可以只丟幾籠並寫原因：`POST /api/discard { slotId, qty, reason }`（不給 qty = 整格，和以前一樣）。

### 2.2 資料表

| 表 | 欄位 | 說明 |
|---|---|---|
| `stocktake` | `warehouse_code`、`created_at`、`slot_count`、`diff_count`、`spoiled_qty`、`action_id` | 一次盤點。全部正確時 `action_id` 是 NULL |
| `stocktake_line` | `stocktake_id`、`slot_id`、`batch_id`、`system_qty`、`counted_qty`、`spoiled_qty`、`reason` | 每一格系統幾籠、實際幾籠、壞幾籠、原因 |

### 2.3 API

| 方法 | 路徑 | 送什麼 | 回什麼 |
|---|---|---|---|
| POST | `/api/stocktakes` | `{ warehouse: 'A', counts: [{ slotId, counted, spoiled?, reason? }] }` | `{ id, warehouse, slotCount, diffCount, spoiledQty, changed, warnings }` |
| GET | `/api/stocktakes?warehouse=A` | — | 盤點紀錄，最新的在前 |
| GET | `/api/stocktakes/:id` | — | 一次盤點的明細 `lines` |

### 2.5 作業統計（`src/stats.js`，`GET /api/stats?days=7`）

給「使用者的抗拒」那題用：用系統自己的時間戳，不用另外拿碼表。

| 欄位 | 意思 |
|---|---|
| `picks` / `puts` | `issued` 發了幾張、`done` 完成、`cancelled` 取消、`open` 還沒回報、`overdue` 超過 30 分鐘沒回報、`medianMinutes` / `avgMinutes` / `maxMinutes` 發單到回報幾分鐘 |
| `stocktakes.A` | `count` 盤了幾次、`daysCovered` 有盤點的天數（李太太要天天盤）、`last` 最後一次 |
| `discrepancy` | 盤點發現數量不符的格數與籠數（越少代表 NO1 的效果越好） |
| `spoiled` | 丟棄／報廢的籠數 |
| `movements` | 各類異動做了幾次（被復原的不算） |

## 2.6 保留的規則怎麼守住

- **寫入一次只跑一個**：`src/db.js` 的 `withTransaction` 開交易前先拿 MySQL 的寫入鎖（`GET_LOCK`）。兩台平板同時發單，第二張一定看得到第一張保留了什麼，不會兩張搶到同一批貨。倉庫只有 36 格，排隊只要幾毫秒。
- **復原／重做前後檢查**（`stock.holdProblems`）：如果這次復原「新」造成某張還沒回報的單拿不到貨、或預定的空格有貨了，整個復原退回，提示先回報或取消那張單。之前就存在的問題（例如盤點改少了）不會擋住無關的復原。
- **取消的單不能重做**：重做停在那張單的出庫／入庫，不會跳過它去重做後面的（順序才不會亂）。
- **盤點、改籠數可以低於保留量**（盤點反映實況），但會回傳提醒，那張單回報時會被擋、要取消重發。
