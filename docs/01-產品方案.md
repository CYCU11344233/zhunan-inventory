## 0. 一句話

> 把兩座冷凍庫做成一塊「會自己算先進先出的數位黑板」：搬運工進庫前就知道要去哪一格拿哪一批；李太太隨時看得到每種菜還剩多少、放了多久。

---

## 1. 個案討論題 1：誰做決策、需要什麼資訊、要收哪些資料

依老師「管理者的資訊世界觀」：真實世界 → 資料 → 作業程序/資料庫 → 資訊 → 決策 → 行動。

| 決策者 | 什麼時候、什麼地點 | 要做的決策 | 需要的資訊（系統呈現） | 要蒐集的真實世界資料 |
|---|---|---|---|---|
| **搬運工**（含兩位公子） | 貨車到、站在冷凍庫門口 | 這批貨**放哪一格** | 哪些櫃位是空的、同品項現在放哪 | 入庫：品項、籠數、日期、放進的櫃位 |
| **搬運工** | 客人要貨、站在冷凍庫門口 | 去**哪一格拿哪一批**、拿幾籠 | FIFO 揀貨單：批次、櫃位、籠數（由舊到新排） | 出庫：實際拿走的批次、籠數 |
| **搬運工** | 整理倉庫時 | 這堆要不要搬去別格 | 目前位置、目標格是否空 | 移位：從哪格到哪格、籠數 |
| **李太太** | 客人來電、在辦公室 | **接不接單**、報多少價 | 該品項現有總籠數、最舊一批放了幾天 | （同上，由搬運工蒐集） |
| **李太太** | 產季前、在辦公室 | **買不買、買多少** | 各品項庫存、庫齡、近期出貨速度、剩餘空櫃位 | 歷史進出紀錄（系統自動累積） |
| **李太太** | 每週/每月 | 哪些貨**快壞了要先出清** | 庫齡警示清單（超過該品項保存天數的批次） | 品項主檔：每種菜可以凍幾天 |

**關鍵洞察**：真正每天在用系統的是搬運工，不是李太太。所以介面要做給「戴著手套、站在冷凍庫門口、拿著手機或平板」的人用——按鈕大、步驟少、一頁搞定。李太太的畫面則是「看報表」。

## 2. 個案討論題 2：三步驟建置系統

### 2.1 建立數位化模型的架構

倉庫的數位模型由四個核心實體組成：

```
冷凍庫 Warehouse (A, B)
  └── 櫃位 Slot  (A-01-1, A-01-2, … 標準化編號：庫-排-層)
        └── 庫存堆 Stock  (某批次的貨放在某櫃位，幾籠)
              └── 批次 Batch  (品項 + 入庫日期；FIFO 的最小單位)
                    └── 品項 Product  (甘藍、高麗菜、… 約 20 種；含保存天數)

異動紀錄 Movement  (每一筆入庫 / 出庫 / 移位 / 盤點 / 丟棄 / 復原，永久保存)
```

- **櫃位標準化編號**是第一步（老師原話：「阿姨，我們來幫每個櫃位標準化，編上號碼好嗎？」）。實體做法：每個櫃位貼一張大字號碼牌。
- **批次 (Batch)** 是本系統和「大黑板」最大的差別。黑板只記「甘藍 5 籠在 A-03」，不記「哪一天進的」，所以做不到先進先出。系統每次入庫都建立一個批次並記錄入庫日期。
- 一個批次可以拆放在多個櫃位（30 籠放不下一格），所以中間有「庫存堆 Stock」把批次和櫃位連起來。

### 2.2 確保模型與真實世界保持同步

原則（老師原話）：**員工的首要職責是確保模型跟真實世界同步**，就像 7-11 店員每次都要掃條碼。

做法：把「記錄」變成搬貨流程的**前置步驟**而不是事後補登。

| 真實世界動作 | 系統流程（先系統、後搬貨） |
|---|---|
| 貨到 | 搬運工在手機點「入庫」→ 選品項、輸入籠數 → 系統**建議空櫃位** → 搬運工放好後按「確認」 → 產生批次 |
| 出貨 | 點「出庫」→ 選品項、輸入籠數 → 系統**印出 FIFO 揀貨單**（去 A-03-2 拿 3 籠、去 B-01-1 拿 2 籠）→ 搬完按「確認」 |
| 整理倉庫 | 在倉庫地圖把那格拖到空格 → 系統記錄移位 |
| 發現數量不對 / 到期日要改 | 在倉庫地圖對該格按右鍵 → 改籠數或到期日 → 系統記錄差異並修正 |
| 壞掉、超期的貨整籠丟掉 | 在倉庫地圖把那格拖到左側「丟棄」區 → 該格清空、記一筆丟棄 |
| 操作錯了 | 紀錄頁按「復原」（或 Ctrl+Z）→ 庫存退回上一步，紀錄不刪、只標記並補一筆「復原」 |

配套規則：
- 沒有經過系統的貨不准進出冷凍庫（李太太要下這道命令，這是管理問題不是技術問題）。
- 所有異動不可刪除，只能用「盤點」修正或「復原」退回，保留完整歷史；復原也是一筆紀錄。
- 介面在手機/平板可用，放在冷凍庫門口。

### 2.3 提供決策支援

| 功能 | 給誰 | 解決什麼 |
|---|---|---|
| **FIFO 揀貨單** | 搬運工 | 不用找、不用想，照單搬；舊貨自動先出，不會再有壓成菜汁的甘藍 |
| **入庫建議櫃位** | 搬運工 | 優先建議同品項附近的空位，找貨時更集中 |
| **倉庫地圖** | 搬運工、李太太 | 一眼看到 A、B 兩庫每一格放什麼、哪裡空 |
| **庫存總覽** | 李太太 | 每種菜幾籠、最舊一批幾天、佔了幾格 |
| **庫齡警示** | 李太太 | 總覽卡片直接標紅（超期）/ 橘（快到期），可一鍵篩選 → 決定出清或降價 |
| **異動紀錄查詢** | 李太太 | 查任何一天進了什麼、出了什麼；日後做採購決策的依據 |

## 3. FIFO 的具體設計（老師埋的考點）

### 3.1 為什麼大黑板做不到

黑板每格只寫「品項 + 數量」，沒有時間維度。同一種菜在三個櫃位各有一批，搬運工不知道哪批最舊，只會拿最近的、最順手的。舊的永遠在最裡面，直到壓爛。

### 3.2 系統怎麼做

1. **入庫時**建立批次，記錄 `入庫日期`。
2. **出庫時**，使用者只輸入「品項 + 幾籠」，系統：
   - 找出該品項所有還有貨的庫存堆
   - 依批次 `入庫日期` 由舊到新排序（同一天的依批次編號）
   - 從最舊的開始扣，扣到滿足需求為止
   - 產生揀貨單：`[櫃位, 批次, 籠數]` 清單
3. 搬運工照揀貨單搬，回來按確認，系統才真正扣庫存。
4. 允許「改單」：如果最舊那批狀況不好，搬運工可以改選其他批次，但系統會記錄「未依 FIFO 出貨」供李太太事後查看。

### 3.3 範例

甘藍菜庫存：

| 批次 | 入庫日期 | 櫃位 | 籠數 |
|---|---|---|---|
| B-20260901-01 | 9/1 | A-03-2 | 3 |
| B-20260910-02 | 9/10 | A-05-1 | 8 |
| B-20260918-01 | 9/18 | B-01-1 | 5 |

客人要 6 籠 → 揀貨單：

1. 去 **A-03-2** 拿 **3 籠**（批次 9/1）
2. 去 **A-05-1** 拿 **3 籠**（批次 9/10）

## 5. 畫面規劃（對應 Demo 頁籤）

1. **總覽** — 總籠數、有貨品項 / 全部品項、超期批次、櫃位使用率進度條；**各品項庫存改成卡片**（20 種菜也能一眼掃完）：每張卡顯示籠數、超期 / 快到期 / 正常的比例條與籠數、幾批 / 佔幾格 / 最舊已放天數，卡片左邊顏色 = 最壞狀態；可搜尋、排序（有問題的排前面 / 籠數 / 名稱）、篩選（有超期 / 有快到期 / 缺貨）；**點卡片展開**列出各格庫存並標出 FIFO 出庫順序，方便審核；展開後有「編輯 / 刪除品項」。卡片最後一格是「＋ 新增品項」（名稱、保存天數、顏色；顏色自動挑沒用過的）。超期 / 快到期就靠卡片顏色與篩選，不另做警示表
2. **入／出庫** — 同一頁，上方切換鈕選「入庫」或「出庫」。
   - 品項用**色塊圖庫**選（每個品項一格：顏色 + 名稱 + 目前籠數，出庫時缺貨的變淡），選完自動收起成一列，不用在 20 個名字的下拉裡找
   - 入庫：可一次登記多項：品項、籠數、櫃位（庫 / 排 / 層三段選，或按「從地圖選格」在**單一庫的小地圖**上點空格；已有貨的格子變淡、表單裡其他項選走的格子標編號）、到期日三種算法（依保存天數 / 指定日期 / 幾天後），表單即時顯示「預計到期」→ 確認後顯示**放貨路線圖**
   - 出庫：可一次登記多項：品項、籠數 → 產生 FIFO 揀貨單 + **揀貨路線圖** → 確認扣帳
3. **倉庫地圖** — 每排是一座直立貨架（3 層），排與排之間用寬空白當走道，地圖置中；上方兩排說明統一為「標記 + 說明」（操作用按鍵樣式、顏色用實際色塊）。**左鍵**看格子資訊（底部面板，只顯示資訊；再點一次或點別處即關閉）、**右鍵**改籠數 / 到期日、**拖到空格** = 移位、**拖到有貨格** = 互換、**拖到左側「丟棄」區** = 整格清空（一拿起格子丟棄區就微亮，方便連續丟超期貨）
4. **紀錄** — 異動流水表（入庫 / 出庫 / 移位 / 盤點 / 改到期日 / 丟棄 / 復原 / 重做）；上方有「復原：上一個動作」「重做」按鈕，任何頁面按 Ctrl+Z / Ctrl+Y 亦可。被復原的紀錄不刪，畫刪除線並標「已復原」，另補一筆「復原」

路線圖的排序規則：「拿哪一批」由 FIFO 決定；「走的順序」依櫃位由入口往裡（庫 → 排 → 層）排列，兩者分開。

Demo 為純前端假資料：模擬李太太的真實狀況，20 種蔬果、隨機籠數 / 入庫日 / 佔格（籠數多的批次會拆放兩格），用固定亂數種子所以每次開啟資料相同。技術設計階段再把它接到 Node + MySQL。

## 6. 假設與待確認

- 每座冷凍庫的排數 × 層數：Demo 先假設 **A 庫 6 排 × 3 層、B 庫 6 排 × 3 層 = 36 格**，實際可在主檔改。
- 計量單位一律用「籠」，不處理公斤。
- 一格只放同一批次（不同批次不混格），但一批可以拆放多格（Stock 表就是做這件事）；若實務上需要混放，Stock 表已可支援。
- 批次的「到期日」預設 = 入庫日 + 品項保存天數，但可在入庫時或事後（地圖右鍵）自訂；狀態判斷（超期 / 快到期）一律看到期日，不看入庫日。
- 「快到期」定義：剩餘天數 ≤ 保存期限的 20%。
- 品項刪除是**軟刪除**：只從選單和總覽消失，舊批次、舊紀錄仍查得到；還有庫存的品項不能刪（先出清）；刪除要輸入品項名稱確認，刪錯可 Ctrl+Z。
- 復原的實作：Demo 用「前後快照」；接後端後改為送反向交易（入庫的反向 = 該批次出庫、移位的反向 = 移回去），紀錄一樣只增不刪。
- 不做登入、不分角色：搬運工和李太太看同一套畫面（李太太主要看總覽，搬運工主要用入／出庫和地圖）。
- 冷凍庫數量擴充（C、D 庫…）：地圖相關畫面一律「一次只畫一座庫」（入庫選格用庫別頁籤切換、路線圖只畫有關的庫），倉庫地圖頁則一座庫一塊往下排；技術方案的 Warehouse 主檔不寫死 A/B。
